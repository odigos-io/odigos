Add an AWS Cloud Connector to manage AWS accounts. The connector runs in the Central cluster, discovers resources across every region enabled in that account, and can instrument AWS Lambda functions when you create Sources.

<Note>
  [Enable Cloud Connectors](/cloud-connectors/enable)
  before you add a connector.
</Note>

## Resource types

| Type | Domain | Discovery | Instrumentation |
| --- | --- | --- | --- |
| `aws.lambda` | Workload | Yes | Yes (OpenTelemetry Lambda layer; [choose a distro](/cloud-connectors/aws/workloads/lambda/distros)) |
| `aws.fargate-task` | Workload | Yes | Yes (agent-staging sidecar in the task definition) |
| `aws.fargate-collector` | Collector | Observes a Collector you deploy (manual mode) | Installs and manages the [regional Collector](/cloud-connectors/aws/regional-collector) (automatic mode). Shown as "Odigos Collector (ECS Fargate)". |
| `aws.ecs-cluster` | Compute platform | Yes | Coming soon |
| `aws.fargate-cluster` | Compute platform | Yes | n/a (coverage only) |

<Info>
  `aws.ecs-cluster` and `aws.fargate-cluster` are compute platforms, reported for
  coverage only; Odigos does not install an agent onto them. They are not offered
  by any access level in the Create Cloud Connector UI. `aws.fargate-task` — an
  individual Fargate **service** — is the ECS resource Odigos instruments directly.
</Info>

aws.lambda and aws.fargate-task support two instrumentation approaches:
- Odigos-managed: The connector automatically applies and maintains the required changes.

- Self-managed: You maintain full control by provisioning through your own CloudFormation, CDK, or Terraform pipelines.

(For a deeper comparison, see [Odigos-managed vs. self-managed instrumentation](/cloud-connectors/overview#odigos-managed-vs-self-managed-instrumentation).)
For the self-managed path, artifact preloading, and per-language CDK/CloudFormation snippets, see the
[AWS Connector](/cloud-connectors/aws/overview) section.

<Note>
  For Lambda, Odigos picks a default OpenTelemetry distro per language. You can
  override it per function, for example to use a lightweight Java handler wrapper
  or AWS ADOT. See [Lambda distros](/cloud-connectors/aws/workloads/lambda/distros).
</Note>

## Add the connector

<Steps>
  <Step title="Open Create Cloud Connector and choose AWS">
    In the Central UI, open **Connections**, click **Create new**, and choose **Cloud Connector**. In the **Create Cloud Connector** drawer, choose **AWS**.
  </Step>

  <Step title="Choose access level">
    Choose how much access this connector should have. The UI shows a **Policy preview** of the IAM policy for the level you pick. You will attach that policy when you create the IAM role or user in the next step.

    <img
      src="/images/cloud-connectors/aws-access-level.png"
      alt="Create Cloud Connector dialog with AWS selected and the Discovery + instrumentation access level showing an IAM policy preview"
    />

    The UI offers four access levels:

    <Tabs defaultTabIndex="1">
      <Tab title="Discovery only">
        The connector can list and discover resources (e.g. Lambda functions and ECS/Fargate resources) but cannot change them or attach instrumentation.

        Use this when you want inventory and visibility first, or if you are managing the environment with Infrastructure as code (IaC).
      </Tab>
      <Tab title="Discovery + instrumentation">
        The connector can discover resources and instrument supported workloads. Prefer this for a full setup in one step.

        Includes all discovery actions, plus Odigos-managed instrumentation for Lambda and Fargate, including the actions used by the ADOT + Application Signals Lambda distro; see [IAM permissions](#iam-permissions).

        Odigos-managed instrumentation also requires an [OTLP destination](/cloud-connectors/instrument-workloads#add-an-otlp-destination) after the connector is online.
      </Tab>
      <Tab title="Discovery + instrumentation + collector">
        Odigos detects and instruments workloads, and installs and manages the regional Collector in your account automatically.

        Includes everything in **Discovery + instrumentation**, plus the permissions Odigos needs to deploy and manage the [regional Collector](/cloud-connectors/aws/regional-collector). The regional Collector also requires [Managed Collectors](/cloud-connectors/enable#managed-collectors) to be enabled on Central.
      </Tab>
      <Tab title="Custom">
        Pick which resource types may be discovered and which may be instrumented, and whether Odigos manages or installs the regional Collector. The UI updates the **Policy preview** to match your selections.

        Use Custom when you need a different mix than the presets (e.g. discover Fargate services but only instrument Lambda).

        <img
          src="/images/cloud-connectors/aws-custom-access.png"
          alt="Custom access level showing the Instrumentation and Collector tables"
        />

        The **Instrumentation** table has a row for **AWS Lambda** and **Amazon ECS (Fargate task)**:

        | Column | Meaning |
        | --- | --- |
        | **Enabled** | Whether Odigos discovers this resource type |
        | **Instrumentation mode** | **Managed by Odigos** (Odigos applies instrumentation automatically) or **Self-managed (IaC)** (you apply the instrumentation through your own pipeline; Odigos does not modify these workloads). Turning on **Managed by Odigos** also turns on **Enabled** |

        The **Collector** table has a row for **Odigos Collector (ECS Fargate)**:

        | Column | Meaning |
        | --- | --- |
        | **Management** | On: Odigos owns the Collector configuration, pushes it over OpAMP, and reports its health. Off: Odigos does not manage a Collector in this account |
        | **Installation** | **Automatic** (Odigos creates and updates the Collector resources in your account) or **Self-managed (IaC)** (you deploy them yourself from the templates Odigos generates). **Automatic** also turns on **Management** |
      </Tab>
    </Tabs>

    For the exact actions each level requires, see [IAM permissions](#iam-permissions).

    <Info>
      Use the policy preview as the source of truth for the permissions policy.
      This keeps connector access scoped — not blanket account admin. See
      [You control the access scope](/cloud-connectors/overview#you-control-the-access-scope).
    </Info>

    Click **Next** to continue to **Setup credentials**.
  </Step>

  <Step title="Setup credentials">
    On the **Setup credentials** screen, apply the IAM policy from the previous step in your AWS account and enter the credentials Odigos will use.

    <img
      src="/images/cloud-connectors/aws-setup-credentials.png"
      alt="Setup credentials screen for an AWS connector with the authentication method set to Assume IAM role and CloudFormation selected as the setup method"
    />

    #### 1. Enter AWS Account ID

    <ParamField path="AWS Account ID" type="string" required>
      The 12-digit ID of the AWS account Odigos will connect to.
    </ParamField>

    #### 2. Choose authentication method

    <Tabs>
      <Tab title="Assume IAM role">
        The default. Odigos assumes a scoped IAM role in your account. Prefer this for production: you attach the permissions policy to the role, and Odigos does not rely on long-lived admin credentials in the connector.

        You enter only the Role ARN and External ID. The connector pod's own identity provides the base credentials, which only need permission to call `sts:AssumeRole` on that role.
      </Tab>
      <Tab title="Access keys">
        Odigos uses IAM user access keys that already have the permissions policy from the access level step attached. There is no role to create.
      </Tab>
      <Tab title="Pod / workload identity">
        Odigos uses the identity of the connector pod, for example IAM Roles for Service Accounts (IRSA) on EKS. Attach the permissions policy from the access level step to that identity. You do not enter any keys.
      </Tab>
    </Tabs>

    #### 3. Choose setup method

    Use the tool that best fits your workflow:

    - **CloudFormation**, **Terraform**, **AWS CLI**, or **Manual** create the IAM role for the **Assume IAM role** method. Each path ends with the same role (trust policy + access-level permissions) and a Role ARN to paste back into Odigos.
    - **IAM user (access keys)** creates an IAM user with the permissions policy attached, for the **Access keys** method.

    #### 4. Create IAM role

    Follow the instructions the UI shows for the method you picked, then copy the **Role ARN**.

    <Tabs>
      <Tab title="CloudFormation">
        1. Set the **External ID** in the UI before you copy the template, so the template and the connector use the same value.
        2. Save the template from the UI as `odigos-connector.yaml`. It creates a role named `OdigosConnectorRole` and takes an `OdigosExternalId` parameter, pre-filled with the External ID you entered (`odigos-connector` if you left it blank).
        3. Deploy it in the target AWS account:

           ```bash
           aws cloudformation deploy \
             --stack-name odigos-connector \
             --template-file odigos-connector.yaml \
             --capabilities CAPABILITY_NAMED_IAM
           ```

        4. Copy the **RoleArn** output from the stack.
      </Tab>
      <Tab title="Terraform">
        1. Open the Terraform snippet in the UI.
        2. Apply it in the target account or module.
        3. Confirm the role was created with the UI trust policy and the permissions policy from the access level step.
        4. Copy the **Role ARN** from the Terraform output or the IAM console.
      </Tab>
      <Tab title="AWS CLI">
        1. Open the AWS CLI commands in the UI.
        2. Run them against the target account (creates the role, trust policy, and attaches permissions).
        3. Confirm the commands completed successfully.
        4. Copy the **Role ARN** from the command output or the IAM console.
      </Tab>
      <Tab title="Manual">
        1. Open the AWS Console → IAM → Roles → Create role.
        2. Select **Custom trust policy**.
        3. Paste the trust policy from the UI (it requires the External ID).
        4. Attach the **permissions policy from the access level step**.
        5. Name the role `OdigosConnectorRole` and create it.
        6. Open the role summary and copy the **Role ARN**.
      </Tab>
      <Tab title="IAM user (access keys)">
        1. In AWS, create or select an IAM user.
        2. Attach the **permissions policy from the access level step**.
        3. Create an access key for that user.
      </Tab>
    </Tabs>

    <img
      src="/images/cloud-connectors/aws-create-iam-role.png"
      alt="Create IAM role step showing CloudFormation instructions and the Enter connector credentials form with IAM Role ARN and External ID fields"
    />

    #### 5. Enter connector credentials

    Paste the values from the previous step into the form.

    <ParamField path="IAM Role ARN" type="string" required>
      ARN of the cross-account role Odigos assumes.
    </ParamField>
    <ParamField path="External ID" type="string">
      Must match the External ID in the role trust policy (e.g. `odigos-connector`). Strongly recommended: set it before copying the setup snippet, since a role created with a blank external ID cannot be assumed.
    </ParamField>
    <ParamField path="Access Key ID" type="string">
      Shown only for the **Access keys** method.
    </ParamField>
    <ParamField path="Secret Access Key" type="string">
      Secret access key for that identity. Shown only for the **Access keys** method.
    </ParamField>

    With **Pod / workload identity** there are no credentials to enter.

    Credentials are stored in a Kubernetes Secret in the Central cluster — never in the connector spec.

    ### Bootstrap region (advanced)

    Select **Show advanced fields** to reveal **Bootstrap region** (default `us-east-1`) and, for the **Access keys** method, **Session Token** (required only for temporary access keys).

    <img
      src="/images/cloud-connectors/aws-bootstrap-region.png"
      alt="Advanced fields on the Setup credentials screen showing the Bootstrap region dropdown"
    />

    <ParamField path="Bootstrap region" type="string" default="us-east-1">
      Region used for initial API calls. This does not limit discovery.
    </ParamField>

    The bootstrap region is the region the connector uses for its first, account-wide calls: the identity check through STS and listing the regions enabled in the account. Change it when your role or organization restricts `us-east-1` for those calls.

    <Warning>
      The bootstrap region does **not** limit discovery. Odigos still discovers
      resources in every region enabled in the account, and the connection test
      checks Lambda and ECS list permissions in every enabled region. If any
      region is denied, the test fails with `access denied in region(s): …` and
      the connector is not created. Your policy must allow discovery in all
      enabled regions.
    </Warning>

    You cannot change the bootstrap region in the UI after the connector is created. To change it, edit `spec.bootstrapRegion` on the `OdigosCloudConnector` resource.
  </Step>

  <Step title="Verify and create">
    Click **Verify & Create Connector**. Central runs connection checks, then creates the credentials Secret and `OdigosCloudConnector` resource when verification succeeds.

    <Info>
      Verification checks authentication, that the credentials belong to the AWS
      Account ID you entered, region enumeration (`ec2:DescribeRegions`), and
      Lambda and ECS list access (`lambda:ListFunctions`, `ecs:ListClusters`) in
      every enabled region. It does not check instrumentation permissions, so for
      **Discovery + instrumentation**, also ensure the instrumentation actions from
      the policy preview are on the role before you create Sources.

      The connection test does not validate Collector permissions. If you chose a
      level that includes the Collector, confirm the Collector actions from the
      policy preview are on the role before you install a Collector.
    </Info>
  </Step>

  <Step title="Wait for Connected">
    After create succeeds, wait until the connector status is **Connected** and initial discovery has completed.
  </Step>
</Steps>

<Check>
  When the connector shows Connected, you can browse discovered workloads and
  start [instrumenting](/cloud-connectors/instrument-workloads).
</Check>

## IAM permissions

Each access level includes the actions of the level before it. The UI policy preview is the source of truth; the tables below list what each level adds.

### Discovery

| Purpose | Actions |
| --- | --- |
| Authentication | `sts:GetCallerIdentity` |
| Region enumeration | `ec2:DescribeRegions` |
| Lambda discovery | `lambda:ListFunctions`, `lambda:ListTags` |
| ECS / Fargate discovery | `ecs:ListClusters`, `ecs:ListServices`, `ecs:DescribeServices`, `ecs:ListTasks`, `ecs:DescribeTasks`, `ecs:DescribeTaskDefinition` |

<Info>
  `ecs:DescribeTaskDefinition` is a discovery permission, not only an
  instrumentation one — it's what lets Odigos see whether a self-managed
  Fargate service already carries your own instrumentation, so grant it
  even if you only ever plan to self-manage instrumentation.
</Info>

### Discovery + instrumentation

Adds Odigos-managed instrumentation for Lambda and Fargate:

| Purpose | Actions |
| --- | --- |
| Read and update function config | `lambda:GetFunctionConfiguration`, `lambda:UpdateFunctionConfiguration` |
| Tag and untag instrumented functions | `lambda:TagResource`, `lambda:UntagResource` |
| Manage OTel layers | `lambda:GetLayerVersion`, `lambda:ListLayers`, `lambda:PublishLayerVersion`, `lambda:DeleteLayerVersion` |
| Manage Fargate task definitions | `ecs:RegisterTaskDefinition`, `ecs:UpdateService`, `ecs:TagResource` |
| Pass task/execution roles when registering a task definition | `iam:PassRole` |
| Access container images in Amazon ECR | `ecr:GetAuthorizationToken`, `ecr:BatchGetImage`, `ecr:GetDownloadUrlForLayer` |
| Set up CloudWatch Application Signals (ADOT + Application Signals distros only) | `iam:GetPolicy`, `iam:ListAttachedRolePolicies`, `iam:AttachRolePolicy`, `iam:GetRole`, `application-signals:StartDiscovery`, `iam:CreateServiceLinkedRole`, `cloudtrail:CreateServiceLinkedChannel` |

<Warning>
  The generated policy grants `iam:PassRole` on all resources (`*`). Scope it yourself
  with the condition `iam:PassedToService=ecs-tasks.amazonaws.com` so the connector can
  only pass roles to ECS tasks.
</Warning>

#### Application Signals actions

The Application Signals actions are only exercised when a Lambda source uses the [ADOT with Application Signals](/cloud-connectors/aws/workloads/lambda/distros#adot-with-application-signals) distro. In that case the connector attaches the AWS-managed `CloudWatchLambdaApplicationSignalsExecutionRolePolicy` policy to the function's execution role and enables Application Signals discovery for the account. It never creates or edits IAM policies.

The generated policy (the UI preview, CloudFormation and Terraform) contains two `Deny` statements at every access level that limit these actions to that managed policy and to the Application Signals service-linked role:

```json
{
  "Sid": "DenyUnrelatedPolicyAttachments",
  "Effect": "Deny",
  "Action": "iam:AttachRolePolicy",
  "Resource": "*",
  "Condition": {
    "ArnNotLike": { "iam:PolicyARN": "arn:*:iam::aws:policy/CloudWatchLambdaApplicationSignalsExecutionRolePolicy" }
  }
}
```

```json
{
  "Sid": "DenyUnrelatedServiceLinkedRoles",
  "Effect": "Deny",
  "Action": "iam:CreateServiceLinkedRole",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": { "iam:AWSServiceName": "application-signals.cloudwatch.amazonaws.com" }
  }
}
```

<Note>
  If you build the policy yourself, keep both `Deny` statements. If you already
  have a connector role, update it with these actions before you select the ADOT
  with Application Signals distro on an Odigos-managed Lambda function.
</Note>

### Collector management (read-only)

Added when Odigos manages a [regional Collector](/cloud-connectors/aws/regional-collector), whether you deploy it yourself (Custom, with **Management** on) or Odigos installs it. These actions only read your infrastructure.

| Purpose | Actions |
| --- | --- |
| ECS cluster details | `ecs:DescribeClusters` |
| Load balancers | `elasticloadbalancing:DescribeLoadBalancers`, `elasticloadbalancing:DescribeListeners`, `elasticloadbalancing:DescribeTargetGroups`, `elasticloadbalancing:DescribeTargetHealth` |
| Networking | `ec2:DescribeVpcs`, `ec2:DescribeSubnets`, `ec2:DescribeSecurityGroups`, `ec2:DescribeRouteTables`, `ec2:DescribeVpcPeeringConnections` |

### Collector deployment

Added when Odigos installs the regional Collector in your account (**Discovery + instrumentation + collector**, or Custom with **Installation** set to **Automatic**).

| Purpose | Actions |
| --- | --- |
| ECS service | `ecs:CreateService`, `ecs:DeleteService`, `ecs:StopTask` |
| Load balancer | `elasticloadbalancing:CreateLoadBalancer`, `elasticloadbalancing:DeleteLoadBalancer`, `elasticloadbalancing:CreateTargetGroup`, `elasticloadbalancing:DeleteTargetGroup`, `elasticloadbalancing:ModifyTargetGroupAttributes`, `elasticloadbalancing:CreateListener`, `elasticloadbalancing:ModifyListener`, `elasticloadbalancing:SetSecurityGroups`, `elasticloadbalancing:AddTags`, `elasticloadbalancing:DescribeTags` |
| Security groups | `ec2:CreateSecurityGroup`, `ec2:DeleteSecurityGroup`, `ec2:AuthorizeSecurityGroupIngress`, `ec2:RevokeSecurityGroupIngress`, `ec2:AuthorizeSecurityGroupEgress`, `ec2:CreateTags` |
| Logs | `logs:CreateLogGroup`, `logs:DeleteLogGroup`, `logs:PutRetentionPolicy`, `logs:TagResource`, `logs:ListTagsForResource` |
| Secrets | `secretsmanager:CreateSecret`, `secretsmanager:PutSecretValue`, `secretsmanager:DescribeSecret`, `secretsmanager:DeleteSecret`, `secretsmanager:TagResource`, `secretsmanager:RestoreSecret` |
| Autoscaling | `application-autoscaling:RegisterScalableTarget`, `application-autoscaling:DeregisterScalableTarget`, `application-autoscaling:PutScalingPolicy`, `application-autoscaling:DescribeScalableTargets`, `application-autoscaling:DescribeScalingPolicies`, `application-autoscaling:ListTagsForResource`, `application-autoscaling:TagResource` |
| Alarms | `cloudwatch:PutMetricAlarm`, `cloudwatch:DeleteAlarms`, `cloudwatch:DescribeAlarms` |

<Warning>
  For the Collector, scope `iam:PassRole` to the Collector task execution role
  ARN, with the condition `iam:PassedToService=ecs-tasks.amazonaws.com`. Odigos
  never creates this role, so do not grant `iam:CreateRole`, `iam:PutRolePolicy`,
  `iam:TagRole`, or `iam:DeleteRole`.
</Warning>
