The **regional Collector** is an Odigos OpenTelemetry Collector that runs in **your** AWS account, with at
most one per region. It runs as an ECS Fargate service behind an **internal** Network Load Balancer (NLB),
and Odigos manages its configuration over OpAMP, so you never edit a Collector config file.

Instrumented workloads in the same region export to the Collector inside your VPC instead of each sending
directly to the backend. That gives you:

- **A short, in-VPC hop.** Workloads export to a regional endpoint, not to the backend across the network.
- **One place for backend credentials.** The Collector holds the credentials for its downstream destinations,
  so workloads don't need them.
- **A central place for routing.** You choose where a region's telemetry goes from the Collectors page in
  Central, without touching the workloads.

<Info>
  The regional Collector is an AWS Connector capability. It is off by default, and your Odigos Central
  installation must enable managed Collectors first. See
  [Prerequisites](#prerequisites).
</Info>

## Which workloads use it

A workload exports through the regional Collector when it is in the same region as the Collector and can
reach it over the network:

| Workload | Uses the Collector? |
| --- | --- |
| Fargate service | Yes, when it can reach the Collector. |
| Lambda function attached to a VPC | Yes, when it can reach the Collector. |
| Lambda function **not** attached to a VPC | Never. It always exports directly to your global destination. Odigos never attaches a function to a VPC or changes its `VpcConfig`. |

A workload can reach the Collector when **all** of the following hold:

- It runs in the **same VPC** as the Collector, or the two VPCs have an **active, same-region VPC peering
  connection** with non-overlapping CIDR blocks and routes in every subnet on both sides.
- The Collector's security group admits the workload's security group or subnet CIDR on TCP ports **4317**
  (OTLP gRPC) and **4318** (OTLP HTTP).

<Warning>
  Odigos does not create VPC peering or any other network connection between your VPCs. If a workload runs in
  a different VPC, set up the peering and routes yourself. Until Odigos can tell that a workload can reach the
  Collector, the workload keeps exporting directly. See [Routing notes](#routing-notes).
</Warning>

## Prerequisites

<Steps>
  <Step title="Enable managed Collectors in Central">
    The Odigos Central Helm chart must have cloud connectors and managed Collectors enabled, with an external
    OpAMP endpoint that Collectors running in AWS can reach. See
    [Managed Collectors](/cloud-connectors/enable#managed-collectors).
  </Step>
  <Step title="An ACTIVE ECS cluster">
    The Collector runs as a service in an ECS cluster you already have. The cluster only needs to be
    `ACTIVE`; it doesn't need other services or EC2 capacity. Odigos never creates a cluster.
  </Step>
  <Step title="A VPC with outbound access">
    The Collector's tasks need egress to pull the image, read Secrets Manager, reach Odigos Central over
    OpAMP, and reach the Collector's downstream destinations. That means a NAT gateway or other central
    egress route for private subnets, or an internet gateway route for public subnets, depending on the
    [outbound path](#install-a-collector-automatic) you choose.
  </Step>
  <Step title="An ECS task execution role">
    The role that ECS uses to start the Collector tasks. **You create it, once per connector in each AWS
    account.** Odigos never
    creates IAM roles. The install wizard gives you a CloudFormation template for it; see step 1 of
    [Install a Collector (automatic)](#install-a-collector-automatic).
  </Step>
  <Step title="IAM permissions on the connector identity">
    The connector uses the credentials you already gave it; there is no separate role for the Collector.
    Select the Collector access level when you add the connector and the permission preview shows exactly
    what the connector needs. See
    [IAM permissions](/cloud-connectors/add-connectors/add-aws-connector#iam-permissions).

    In automatic mode, the connector's policy also needs `iam:PassRole` for the **ARN of your Collector execution role** (in addition to the `iam:PassRole` that Fargate instrumentation uses), with the condition
    `iam:PassedToService` equal to `ecs-tasks.amazonaws.com`.

    <Warning>
      Never grant `iam:CreateRole`, `iam:PutRolePolicy`, `iam:TagRole`, or `iam:DeleteRole` to the connector.
      It doesn't need them.
    </Warning>
  </Step>
</Steps>

<Note>
  The connection test doesn't check Collector permissions. A connector can pass the test and still fail to
  install or manage a Collector if the permissions for your chosen mode are missing.
</Note>

## Modes

The Collector mode is set **per connector**.

| Mode | What you do | What Odigos does | What Odigos never does |
| --- | --- | --- | --- |
| **Off** | Nothing. | Nothing. Workloads export directly. | Create or read Collector infrastructure. |
| **Manual (customer IaC)** | Deploy the Collector yourself from generated IaC. | Finds the Collector by its tags, observes it, pushes its configuration over OpAMP, and routes workloads to it once it is ready. | Create, repair, or delete any of your infrastructure. |
| **Automatic** | Create the execution role once, then run the install wizard. | Everything in Manual, plus creates and keeps in sync the ECS service, task definition, internal NLB, listeners, target groups, security group, log group, Secrets Manager secrets (the OpAMP credential, the license, and, when needed, a startup configuration), and autoscaling when it is enabled. | Create your ECS cluster, VPC, or execution role. |

Both modes need an `ACTIVE` ECS cluster and an ECS task execution role that you provide.

### Choose a mode when you create the connector

In the access level step of the connector wizard:

- Select **Discovery + instrumentation + collector** for **Automatic**.
- Select **Custom** and use the **Collector** section for finer control. The **Management** and
  **Installation** toggles map to the modes: Management alone is Manual, Management plus Installation is
  Automatic.

### Change the mode later

<Steps>
  <Step title="Open the row action">
    On the **Connections** page, open the action menu on the connector's row and choose **Collector mode**.
  </Step>
  <Step title="Pick a mode">
    In the **Regional Collector mode** drawer, choose **Off**, **Manual (customer IaC)**, or **Automatic**.
  </Step>
  <Step title="Save">
    Click **Save and restart connector**.
  </Step>
</Steps>

<Warning>
  Changing the mode **restarts the connector**. Only Central administrators can change it.
</Warning>

## Install a Collector (automatic)

In automatic mode, Odigos deploys the Collector for you. Select the connector on **Connections**, then open
**Collectors** in the left navigation. The page is titled **Managed Collectors**. Click **Install new
collector** (or **Install collector** from an empty state) to open the install wizard.

The wizard has three phases, **Prepare**, **Configure**, and **Verify**, across nine steps. At the top, a
method switch lets you view each step as an **Overview**, as **AWS CLI** commands, or as a
**CloudFormation** template.

<Steps>
  <Step title="Pre-create the Collector task execution role">
    The wizard gives you a CloudFormation template for the execution role. Deploy it, then paste the role ARN
    from the stack output **`ExecutionRoleArn`**.

    <img
      src="/images/cloud-connectors/aws-collector-execution-role.png"
      alt="Install collector wizard, step 1, showing the execution role CloudFormation template and the Execution role ARN field"
    />

    - Set the **`ConnectorName`** parameter to the **exact name of this connector**. The permissions in the
      role are scoped by that name.
    - Deploy the stack **once per connector in each AWS account**. IAM roles are account-wide, so a role you
      already created for one region works for the others.
    - The role can be assumed by `ecs-tasks.amazonaws.com`, restricted to your account. It can write to the
      Collector's log group and read the Collector's secrets, and nothing else.
    - If you pull the Collector image from a **private ECR** repository, the role also needs
      `ecr:GetAuthorizationToken`, `ecr:BatchCheckLayerAvailability`, `ecr:BatchGetImage`, and
      `ecr:GetDownloadUrlForLayer`.
    - If your secrets are encrypted with a **customer-managed KMS key**, the role also needs `kms:Decrypt`
      on that key.

    Remember to allow the connector's `iam:PassRole` for this role's ARN (automatic mode). See
    [Prerequisites](#prerequisites).
  </Step>
  <Step title="Select the Collector region">
    Choose the region for this Collector. There is at most one Collector per region, and only workloads in
    that region use it.
  </Step>
  <Step title="Choose the ECS cluster">
    Enter the ARN of an existing `ACTIVE` ECS cluster. Odigos does not create the cluster, and the cluster
    needs no other services or EC2 instances.
  </Step>
  <Step title="Choose the VPC">
    Enter the VPC ID. Odigos picks the subnets itself: subnets with free IP addresses and a usable outbound
    route, preferably spread over at least two Availability Zones. You can see the choice later on the Collector's
    overview.
  </Step>
  <Step title="Choose the outbound path">
    This controls how the Collector tasks reach the internet: for image registries, Secrets Manager, the
    Odigos OpAMP endpoint, and the Collector's downstream destinations.

    | Option | Task public IP | Your VPC needs |
    | --- | --- | --- |
    | **Private** | No | A default route to a NAT gateway or central egress. |
    | **Public** | Yes | A route to an internet gateway. |

    The Collector's load balancer is **internal** either way. Workloads never reach it from the internet.
  </Step>
  <Step title="Choose the Collector size">
    Each task gets a fixed amount of CPU and memory. **Medium** is the default.

    | Size | vCPU | Memory |
    | --- | --- | --- |
    | Small | 0.5 | 1 GiB |
    | **Medium** (default) | 1 | 2 GiB |
    | Large | 4 | 8 GiB |
    | X-Large | 8 | 16 GiB |
    | 2X-Large | 16 | 32 GiB |

    <img
      src="/images/cloud-connectors/aws-collector-size.png"
      alt="Install collector wizard showing the Collector size options from Small to 2X-Large"
    />

    By default the service runs **2 tasks** and keeps Collector logs for **7 days**.
  </Step>
  <Step title="Prepare automatic scaling">
    ECS autoscaling needs the Application Auto Scaling service-linked role for ECS. The wizard shows the
    command that creates it if your account doesn't have it yet:

    ```bash
    aws iam create-service-linked-role \
      --aws-service-name ecs.application-autoscaling.amazonaws.com
    ```

    You only need this role if the Collector uses automatic scaling. By default it runs a fixed number of
    tasks, so you can skip the command.
  </Step>
  <Step title="Review and install">
    Review the summary, then click **Install Collector**. This is the step that creates resources in your
    AWS account.

    <img
      src="/images/cloud-connectors/aws-collector-review.png"
      alt="Install collector wizard review step summarizing the execution role, region, cluster, VPC, outbound path, and size, with the Install Collector button"
    />
  </Step>
  <Step title="Verify">
    Odigos shows the Collector's progress until it reports **Healthy**. See
    [Collector status](#collector-status).
  </Step>
</Steps>

<Info>
  By default the Collector gets its own security group. It admits OTLP traffic from the security groups of
  the enabled Fargate services and VPC-attached Lambda functions that can reach it. Only if Odigos can't
  resolve those security groups does it fall back to admitting the Collector VPC's CIDR range, and it
  reports the Collector as degraded while that fallback is in effect. When
  Odigos has to choose, it prefers subnets with private egress, at most one per Availability Zone, across up
  to three zones. If only one Availability Zone is usable, the Collector runs with reduced availability.
</Info>

## Install a Collector (manual)

In manual mode you deploy the Collector with your own infrastructure-as-code. Odigos renders the IaC, issues
the credential the Collector uses to connect to Central, and takes over configuration once the Collector
connects. It never creates, repairs, or deletes your resources.

<Steps>
  <Step title="Open the install wizard">
    On **Collectors**, click **Install new collector** (or **Install collector** from an empty state).
    Choose the region, ECS cluster, and VPC as in the
    automatic flow, and pre-create the [execution role](#install-a-collector-automatic).
  </Step>
  <Step title="Enter your subnets and security group">
    Fill in **Collector subnet IDs** and **Collector security group ID**. Create the security group and the
    CloudWatch log group (`/odigos/collector/<connector>`) yourself first.

    <Warning>
      On the Collector security group, allow inbound **TCP 4317 and 4318** from your workloads' security
      groups or subnets. Without it, workloads cannot reach the Collector and keep exporting directly. The
      wizard doesn't add these rules for you.
    </Warning>
  </Step>
  <Step title="Save the Collector configuration">
    Click **Save Collector configuration**. This only records your choices in Odigos. **It creates nothing in
    AWS.**
  </Step>
  <Step title="Create the credential secret">
    Create an empty Secrets Manager secret named `odigos/collector/<connector>/<region>/credential`. Then
    click **Issue credential** and put the value in the secret.

    <Warning>
      The credential is shown **once**. Copy the complete header and store it in the AWS secret before you
      deploy the ECS service. It can't be retrieved after the wizard closes. Issuing a credential needs the
      Central owner or admin role.
    </Warning>
  </Step>
  <Step title="Create the license secret">
    Create a second secret named `odigos/collector/<connector>/<region>/license` with this value, using your
    on-prem token:

    ```json
    {"username":"odigos","password":"<ON_PREM_TOKEN>"}
    ```
  </Step>
  <Step title="Deploy">
    In **Deploy method**, choose **CloudFormation**, **AWS CLI**, or **Terraform**. The wizard renders the
    document with your values. Fill in the remaining placeholders it lists under **Fill these in before
    applying**. You can open the same documents later from **Download config** on the Collectors page.

    Apply them with your own IaC principal, not the connector's.
  </Step>
  <Step title="Verify">
    Wait for the Collector to connect and report **Healthy**. See [Collector status](#collector-status).
  </Step>
</Steps>

Tag the resources you create so Odigos can find them:

| Tag | Value |
| --- | --- |
| `odigos-component` | `collector` |
| `odigos-connector` | The connector name |
| `odigos-connector-id` | The connector ID |
| `odigos-region` | The Collector's region |
| `odigos-network` | The ID of the VPC the Collector runs in |
| `odigos-iac` | `customer` |

The rendered IaC includes these tags, so keep them as generated.

## Route workloads to the Collector

Creating a Collector doesn't move any traffic. Workloads switch over when you add a routing destination.

<Steps>
  <Step title="Add the destination">
    On the connector, add a destination of type **Odigos Managed Regional Collector** and choose the
    **Region**. The type is only offered once the Collector capability is on and a Collector in a region has
    an endpoint.

    <Tip>
      Keep a **global OTLP destination** (OTLP gRPC or OTLP http) configured as well. Workloads that can't
      reach the Collector fall back to it, including non-VPC Lambda functions and workloads in other
      networks. This is recommended.
    </Tip>
  </Step>
  <Step title="Wait for the Collector to be ready">
    Odigos only routes to a Collector after it has reported ready at least once. After that, the decision is
    remembered, so a later blip in readiness doesn't send everything back to direct export.
  </Step>
  <Step title="Workloads cut over">
    Eligible workloads are updated to export through the Collector. How that happens depends on whether you
    have a global destination.
  </Step>
</Steps>

A workload goes through the Collector only when **all** of these are true:

- A routing destination exists for the Collector's region.
- The Collector has an endpoint.
- The Collector has reported ready at least once.
- The workload can [reach the Collector](#which-workloads-use-it).

### Cutover behavior

<Tabs>
  <Tab title="With a global destination">
    The cutover is gradual, so one bad rollout doesn't hit everything at once.

    - Once the Collector is ready and there are eligible instrumented workloads, Odigos announces a
      **one-minute warning window**. Nothing moves until it ends.
    - Workloads then move in **batches of up to 10** per pass by default, shared between Fargate services
      and Lambda functions.
    - Each moved workload gets a **new revision**: a new task definition revision for a Fargate service, or an
      updated configuration for a Lambda function.
    - Failed cutovers are retried, oldest first. At most half of each batch is retries, so workloads that
      haven't been tried yet are never starved.

    Workloads waiting for their turn keep using the global destination.
  </Tab>
  <Tab title="Without a global destination">
    There is nothing to fall back to, so there is no gradual cutover. Workloads route to the Collector
    **immediately** after it first reports ready.
  </Tab>
</Tabs>

To stop using the Collector, **disable** the routing destination. All workloads return to direct export.

### Where the Collector sends data

The routing destination only chooses the path *to* the Collector. Where the Collector sends telemetry next
is configured separately, per region, on the Collectors page.

<Steps>
  <Step title="Open the Collector">
    On **Collectors**, select the region.
  </Step>
  <Step title="Add a downstream destination">
    In the **Destinations** card, click **Add destination** and choose the backend. The table shows each
    destination's type, name, signals, and status.
  </Step>
</Steps>

<Warning>
  A Collector with **no downstream destination accepts telemetry and discards it.** Add at least one before
  routing workloads to it. Profiles aren't accepted by the Collector.
</Warning>

## Collector status

Select a region on the Collectors page to see its status badge.

| Status | Meaning |
| --- | --- |
| **Pending**, **Deploying**, **Deleting** | A change is in progress. |
| **Awaiting customer** | Odigos is waiting for you to deploy the Collector (manual mode). |
| **Healthy** | The Collector is ready and connected to Central. |
| **Degraded** | The Collector isn't fully healthy, or it has stopped checking in. |
| **Error** | The last operation failed. |

If a Collector stops checking in, a banner explains the effect:

> This collector has not checked in recently. It may still be exporting, but its configuration can no longer be changed.

The region's overview shows:

| Card | Contents |
| --- | --- |
| Gauges | **CPU** and **Queue depth** |
| **Throughput** | Accepted spans, dropped spans, uptime |
| **Resources** | CPU and memory size, memory in use, and whether the Collector is enabled |
| **Placement** | Execution role, ECS cluster, VPC, public task IP, and subnets (**Selected by Odigos** or **Pinned**) |
| **Runtime** | gRPC and HTTP endpoints, tasks, config, first ready time |
| **Destinations** | The Collector's downstream destinations |

The action buttons on the overview are **Reconfigure** and **Uninstall**. Use **Refresh** at the top of the
page to reload the status. **Download config** (manual mode only) opens the copyable IaC for the Collector.

### Routing notes

When a workload exports directly instead of through the Collector, its status shows a note that says why.

| Note | Meaning |
| --- | --- |
| `Defaulting to the global OTLP destination: the Odigos Managed Regional Collector has not reported ready yet.` | The Collector hasn't been ready yet. The workload moves once it is. |
| `Defaulting to the global OTLP destination: the Odigos Managed Regional Collector has no ingress endpoint yet.` | The Collector exists, but its load balancer endpoint isn't published yet. |
| `Defaulting to the global OTLP destination: this Lambda has no VPC configuration, so it cannot reach the Odigos Managed Regional Collector. Odigos will not attach the function to a VPC or change its VpcConfig.` | A Lambda function without a VPC. This is permanent by design. |
| `Defaulting to the global OTLP destination: no Odigos Managed Regional Collector is set up in this region.` | The routing destination exists, but this region has no Collector. |
| `Defaulting to the global OTLP destination: the Odigos Managed Regional Collector is not known to be reachable from this workload's network.` | A Fargate service in a different VPC without peering, with overlapping CIDRs or missing routes, or one the Collector security group doesn't admit. For a Fargate service, the note starts with the workload's VPC ID and what to fix. See [Which workloads use it](#which-workloads-use-it). |
| `Defaulting to the global OTLP destination: this VPC-attached Lambda cannot currently reach the Odigos Managed Regional Collector. ...` | The same for a VPC-attached Lambda function. The note goes on to list what to fix. |
| `Continuing to use the global OTLP destination until this workload is admitted to the regional Collector rollout.` | The workload is eligible but waiting for its batch. |
| `Cannot export telemetry through the Odigos Managed Regional Collector: <cause>, and no global OTLP destination is configured for fallback.` | There is no global destination, so the workload can't export at all. Fix the cause or add a global destination. |

During a cutover, the Collector reports `N workload cutover(s) in <region> failed and will be retried. Examples: <workloads>.`
when some workloads couldn't be moved yet. The one-minute warning shows as:

> The regional Collector is ready. New workload cutovers are announced and will begin after the one-minute warning window, in bounded batches.

## Uninstall

<Tabs>
  <Tab title="Automatic">
    On the region's overview, click **Uninstall**. Odigos revokes the Collector's credentials, then deletes
    the resources it created: the ECS service and its tasks, any autoscaling target and policies, the load
    balancer and its listeners, the target groups, the security group, the Collector's secrets, and its log
    group. It retries the security group while network interfaces release. **Deleting** can last up to 30
    minutes. After that it moves to **Error** and Odigos keeps retrying. Task definition revisions, the
    execution role, the cluster, and the VPC stay in your account.
  </Tab>
  <Tab title="Manual">
    Click **Remove from Odigos**. Odigos revokes the Collector's credential and removes its declaration. **The
    resources you deployed stay in your account.** Delete them with the same IaC you used to create them.
  </Tab>
</Tabs>
