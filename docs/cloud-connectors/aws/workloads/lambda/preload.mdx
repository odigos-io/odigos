<Note>
  If you use **Odigos-managed** Lambda instrumentation, you can skip this page — the
  connector publishes the layer version into your account itself
  (`lambda:PublishLayerVersion`) the first time it instruments a function. Nothing to
  preload. Those layers get the description
  `Odigos OpenTelemetry layer for <lang>/<arch> sha256:<digest prefix>`, and the connector publishes a new
  layer version whenever the bundle's digest changes.
</Note>

If you **self-manage** instrumentation, you have two choices for where the layer your CloudFormation, CDK,
or Terraform attaches actually lives. Either way, the layer must be **v0.0.18 or newer**: older layers don't
contain the launcher that reads `ODIGOS_LAMBDA_CONFIG`. See
[What gets added to your function](/cloud-connectors/aws/workloads/lambda/instrument#what-gets-added-to-your-function).

<Tabs>
  <Tab title="Reference the public Odigos layer">
    Simplest option: attach the public layer ARN Odigos publishes in every supported region directly in your
    function resource:

    ```text
    arn:aws:lambda:<region>:233171357117:layer:odigos-otel-<family>-<arch>:<n>
    ```

    `<arch>` is `x86_64` or `arm64`, and `<family>` is one of:

    | Family | Used by |
    | --- | --- |
    | `java`, `nodejs`, `python`, `ruby` | The default OpenTelemetry distros |
    | `adot-java`, `adot-nodejs`, `adot-python` | The [AWS ADOT distros](/cloud-connectors/aws/workloads/lambda/distros#aws-adot) (SDK layer) |
    | `adot-collector` | The collector layer every ADOT distro also needs |

    ADOT functions need **both** the SDK layer and the collector layer attached, so they use two of the
    function's five layer slots.

    No preloading, no extra deploy — for next steps see
    [Instrument Lambda](/cloud-connectors/aws/workloads/lambda/instrument). If your organization's policy
    forbids attaching a Lambda layer owned by another AWS account, use the
    **Preload into your own account (SAR)** tab instead.
  </Tab>

  <Tab title="Preload into your own account (SAR)">
    Deploy the Odigos layer from the AWS Serverless Application Repository (SAR) so the resulting
    `AWS::Lambda::LayerVersion` is owned by **your** account. Then attach that stack's `LayerVersionArn`
    instead of the public Odigos layer ARN.

    Deploying a SAR application is an AWS workflow — follow
    [Deploying applications](https://docs.aws.amazon.com/serverlessrepo/latest/devguide/serverlessrepo-how-to-consume.html)
    (Console or CLI). For nesting the app in your own template, see
    [`AWS::Serverless::Application`](https://docs.aws.amazon.com/serverless-application-model/latest/developerguide/sam-resource-application.html).

    What Odigos supplies for that deploy:

    - **Application IDs** — `SAR_APPLICATIONS` in `@odigos/aws-cdk`, keyed by `language/architecture`
      (for example `python/arm64`). The applications are published from account `233171357117` in
      `us-east-1`, named `odigos-otel-<family>-<arch>`, and you can search the console for that name. The
      families are the same as the public layers above.
    - **Semantic version** — `SAR_SEMANTIC_VERSION` in the same package. Pin it (for example `0.0.18`); SAR
      versions are immutable and that pin keeps the layer bytes stable across deploys.

    <Note>
      SAR application names spell the x86 architecture with a hyphen (`odigos-otel-python-x86-64`), while the
      layer names and ARNs use an underscore (`odigos-otel-python-x86_64`).
    </Note>

    With the Odigos CDK construct, you do not call SAR yourself — set
    `layerSource: OdigosLayerSource.IN_ACCOUNT` and the construct nests the application using those exports.
    For an ADOT distro, the construct nests **two** SAR applications: the SDK and the collector.
    See [Where the layer comes from](/cloud-connectors/aws/cdk/lambda#where-the-layer-comes-from).
    The deploying principal needs `serverlessrepo:CreateCloudFormationTemplate` and
    `serverlessrepo:GetApplication`.

    <Info>
      Layer versions are retained, never deleted, when a stack update supersedes them
      — a function still pinned to an older version would break at cold start the
      moment it disappeared. Clean up old versions yourself once nothing references
      them.
    </Info>
  </Tab>
</Tabs>

## Layer integrity

The ADOT SDK layers are repackaged from the official AWS ADOT releases. Each download is verified against a
pinned SHA-256 checksum when the layers are built, and a mismatch fails the build. Layers the connector
publishes into your account carry the bundle's SHA-256 digest prefix in their description, so you can tell
which bundle a given layer version contains.
