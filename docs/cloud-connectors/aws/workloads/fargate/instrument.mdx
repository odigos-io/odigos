This page shows how to instrument an ECS **service** running on Fargate yourself via CloudFormation, by editing its task
definition directly — no changes made by the connector on your behalf. Odigos still discovers the service
and reports its status once your changes are in place; see
[Odigos-managed vs. self-managed instrumentation](/cloud-connectors/overview#odigos-managed-vs-self-managed-instrumentation)
for how that works. 

<Tip>
  You don't have to assemble these values by hand. In Central, open the service's drawer and use the
  **How to instrument this workload** panel — it generates these snippets for the selected service,
  with your destination's endpoint, protocol, and signals filled in.
</Tip>

<Info>
  Prefer the Odigos CDK construct? See
  [CDK: Fargate](/cloud-connectors/aws/cdk/fargate). This page is the
  hand-written CloudFormation / raw ECS form of the same change.
</Info>

## How it works

Self-managed Fargate instrumentation adds one extra container to your task definition, plus a handful of
environment variables on your application container. Here's what happens each time the task starts:

1. A small helper container, **`odigos-agent`**, starts first. It copies the files your application's
   language agent needs into a shared volume, then exits. It's marked non-essential, since its only job is
   to prepare files — it isn't part of your running application.
2. Your **application container** waits for step 1 to finish successfully before it starts
   (`DependsOn: ... Condition: SUCCESS`) — this guarantees the agent files are already in place by the time
   your code runs.
3. Your application container picks up the agent through environment variables specific to its language —
   for example `JAVA_TOOL_OPTIONS` for Java — and begins exporting telemetry.

<Info>
  There's no intermediate collector inside the task — each Fargate task sends
  telemetry **directly** to its OTLP endpoint (your destination, or the regional
  Collector when one serves the service), so that endpoint must be reachable from
  the task's network. See
  [Telemetry export](/cloud-connectors/aws/overview#telemetry-export).
</Info>

## CloudFormation

Merge these properties into your task definition. Only the exact agent path, activation variable, and network protocol change per language. Pick yours below:

<Tabs>
  <Tab title="Java">
    ```yaml
    # Merge into Resources.<YourTaskDefinition>.Properties
    Volumes:
      - Name: odigos-agent   # ephemeral-storage bind mount, scoped to the task
    ContainerDefinitions:
      - Name: odigos-agent
        Image: "registry.odigos.io/odigos-fargate-agents:<version>"
        Essential: false
        Command: ["sh", "-c", "mkdir -p /var/odigos && cp -r /instrumentations/java /var/odigos/java"]
        MountPoints:
          - SourceVolume: odigos-agent
            ContainerPath: /var/odigos
      - Name: "<YOUR_CONTAINER>"
        # ... your existing configuration ...
        MountPoints:
          - SourceVolume: odigos-agent
            ContainerPath: /var/odigos
            ReadOnly: true
        DependsOn:
          - ContainerName: odigos-agent
            Condition: SUCCESS
        Environment:
          - Name: ODIGOS_IAC
            Value: '{"v":1,"lang":"java","image":"registry.odigos.io/odigos-fargate-agents:<version>"}'
          - Name: OTEL_SERVICE_NAME
            Value: "<YOUR_SERVICE_NAME>"
          - Name: OTEL_RESOURCE_ATTRIBUTES
            Value: "cloud.provider=aws,cloud.platform=aws_ecs,cloud.region=<REGION>"
          - Name: OTEL_EXPORTER_OTLP_ENDPOINT
            Value: "<OTLP_ENDPOINT_URL>"
          - Name: OTEL_EXPORTER_OTLP_PROTOCOL
            Value: "http/protobuf"   # or "grpc" — must match your destination; see note below
          - Name: OTEL_SDK_DISABLED
            Value: "false"
          # "otlp" for each signal the destination enables, "none" for each it doesn't
          - Name: OTEL_TRACES_EXPORTER
            Value: "otlp"
          - Name: OTEL_METRICS_EXPORTER
            Value: "otlp"
          - Name: OTEL_LOGS_EXPORTER
            Value: "otlp"
          # APPEND after any existing value, joined by a space — assigning discards yours.
          - Name: JAVA_TOOL_OPTIONS
            Value: "<YOUR_EXISTING_VALUE> -javaagent:/var/odigos/java/javaagent.jar"
    ```

### Rules that apply to every language

<AccordionGroup>
  <Accordion title="ODIGOS_IAC is per container">
    It's the only thing marking a container as instrumented: its presence, with a valid JSON value, is what counts.
    Odigos reads two fields from it. `lang` names the agent you staged, and Odigos uses it as the container's language;
    a runtime override on the Source takes precedence, and a `lang` that disagrees with it is reported as drift. Leave
    `lang` out and Odigos detects the language from the container itself. `image` records the agents image you staged from — Odigos holds the
    task to *that* image, so pinning or mirroring the image isn't reported as out of date; leave it out and the
    `odigos-agent` container is checked for being present, non-essential, and staging the right agents, whatever its tag.
    `v` is the schema version (`1`). All marked containers in one task definition must record the same `image`. Use
    the same value as the `odigos-agent` container's `Image`. Never set `ODIGOS_MANAGED` — that's the
    connector's own rollback record, written only when you hand the workload to Odigos-managed
    instrumentation instead.
  </Accordion>

  <Accordion title="Signals">
    Odigos compares the three `OTEL_*_EXPORTER` variables with the signals your destination has enabled, and
    expects each to be exactly `otlp` (enabled) or `none` (disabled). A missing signal and an extra one are
    both reported as drift, so always set all three. `OTEL_SDK_DISABLED` must be `false`, and Python's
    `OTEL_PYTHON_LOGGING_AUTO_INSTRUMENTATION_ENABLED` must be `true` when logs are enabled and `false`
    otherwise. Ruby produces traces only, and no Fargate agent produces profiles.
  </Accordion>

  <Accordion title="Never set per-signal exporter variables">
    Don't set `OTEL_EXPORTER_OTLP_TRACES_*`, `OTEL_EXPORTER_OTLP_METRICS_*`, or `OTEL_EXPORTER_OTLP_LOGS_*`
    variables (`ENDPOINT`, `PROTOCOL`, `HEADERS`, or `INSECURE`) on an instrumented container. They override the
    destination, and Odigos reports their presence as drift. Use the shared `OTEL_EXPORTER_OTLP_ENDPOINT` and
    `OTEL_EXPORTER_OTLP_PROTOCOL` shown above.
  </Accordion>

  <Accordion title="Endpoint and protocol are one decision">
    Both are compared exactly against what your OTLP destination resolves to on this connector. If the
    destination offers OTLP/HTTP, every language is expected to use it with `http/protobuf`; if it only
    offers OTLP/gRPC, use the gRPC endpoint written as a URL with a scheme (for example `https://<host>:4317`) and
    `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` instead of the `http/protobuf` shown above (except PHP and Ruby, which
    support HTTP only — see their tabs). Pairing an endpoint with the wrong transport fails at runtime as an
    opaque connection reset. Copy the exact endpoint from the **How to instrument this workload** panel.

    If your destination needs headers (for example an API key), set `OTEL_EXPORTER_OTLP_HEADERS` to a
    comma-separated `key=value` list, sorted by key, with both names and values URL-encoded (a space becomes
    `+`). It's compared exactly like the endpoint. If the destination has no headers, don't set the variable.
  </Accordion>

  <Accordion title="One odigos-agent container serves the whole task">
    Its `Command` is per task, not per language. A task definition with application containers in more than
    one language needs a chained `&& cp -r /instrumentations/<lang> /var/odigos/<lang>` for each, in
    alphabetical order — Odigos compares the command exactly against the union of every marked container's
    language.
  </Accordion>

  <Accordion title="OTEL_SERVICE_NAME is the ECS service name">
    Set `<YOUR_SERVICE_NAME>` to your ECS service's name — not the task definition family, the container name, or
    the cluster-prefixed name the source is listed under in Odigos. If you've set a reported service name on the
    source, use that. A different value is reported as drift.
  </Accordion>

  <Accordion title="Debug logging">
    Leave `OTEL_LOG_LEVEL` unset. Odigos expects it absent, and reports it as drift, unless debug telemetry is
    enabled on the connector — in which case it expects `OTEL_LOG_LEVEL=debug`.
  </Accordion>

  <Accordion title="Roll the service, not just the revision">
    Registering a new task-definition revision isn't enough on its own — update the service to it, or it
    keeps running the old one.
  </Accordion>

  <Accordion title="Constraints">
    A 10-container task-definition limit, Linux-only agents bundle (no Windows tasks), and the
    `odigos-agent` container must stay non-essential — ECS only accepts a `SUCCESS` dependency against a
    non-essential container.
  </Accordion>

  <Accordion title="Registry reachability">
    The image is pulled at every task start. If your task's subnet can't reach
    `registry.odigos.io`, mirror the image into a registry it can — see
    [Preload artifacts](/cloud-connectors/aws/workloads/fargate/preload).
  </Accordion>
</AccordionGroup>

## Existing environment and multiple containers

Workload-level runtime overrides apply before automatic selection, including when the image language or
PHP/Ruby major.minor version cannot be detected. For several application containers, use named container
overrides. Mixed-language tasks receive container-specific reference instructions with one shared staging
container and volume.

Automatic injection preserves image `ENV` loader settings when image configuration can be read. When using
ECS environment files, inline their values in the task definition and remove `environmentFiles` before
automatic instrumentation. Odigos refuses hidden file contents because it cannot safely verify loader or
per-signal transport settings. Remove image-level per-signal OTLP overrides as well. In CDK, use
`existingLoaderValue` for values unavailable at synthesis. Values delivered through ECS secrets must be
resolved explicitly rather than duplicated as ordinary environment variables. .NET instrumentation supports
glibc images; Alpine/musl is rejected when detected.
