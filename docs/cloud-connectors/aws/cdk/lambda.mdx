`OdigosLambdaInstrumentation` instruments AWS Lambda functions defined in your CDK app.

<Note>
  Read [Odigos AWS CDK](/cloud-connectors/aws/cdk/overview) first — it covers
  installing the package and how Odigos recognizes an instrumented workload — then
  [Destinations](/cloud-connectors/aws/cdk/destinations) for the shared `destination`
  options. This page covers only what's specific to Lambda.
</Note>

## Basic usage

```typescript
import { OdigosLambdaInstrumentation } from '@odigos/aws-cdk';

new OdigosLambdaInstrumentation(this, 'Odigos', {
  destination: { endpoint: 'otlp.example.com:4317' },
  functions: [apiFn, workerFn],
});
```

Typically you define **one** `OdigosLambdaInstrumentation` per CDK stack and pass it every function you
want instrumented. One construct does everything for every function you list: attaches the right
OpenTelemetry layer for that function's language and CPU architecture, sets the exec wrapper that loads it,
configures where telemetry goes, and tags the function so Odigos recognizes it (see
[How Odigos recognizes your workload](/cloud-connectors/aws/cdk/overview#how-odigos-recognizes-your-workload)).

`serviceName` (and other construct-level options) apply to **every** function on that construct. If each
function needs its own `serviceName`, define **one construct per function** instead of listing them
together. The same applies whenever any other setting must differ — including [`distro`](#choosing-a-distro). To instrument every function in the
stack without listing them, use the [Aspect](#instrumenting-every-function-in-a-stack) instead.

Languages supported: **Java, Python, Node.js, Ruby.** Each has a default distro, and most have alternatives —
see [Choosing a distro](#choosing-a-distro). Other runtimes — Go, .NET, and custom runtimes —
have no OpenTelemetry Lambda layer, so they can't be instrumented this way.

<Info>
  You can also call `instrument(fn)` or `instrumentAll([fn1, fn2])` on the construct
  after creating it, instead of passing `functions` up front.
</Info>

## How telemetry leaves the function

This is worth understanding because it explains several of the options below.

The construct writes two environment variables on each function: `AWS_LAMBDA_EXEC_WRAPPER` (which
loads the instrumentation) and `ODIGOS_LAMBDA_CONFIG` (a readable JSON document, schema version 2, with the service name, the
enabled signals, and the destination — `version`, `service`, `signals`, `endpoint`, `http`, `insecure`, `headers`, `applicationSignals`, `functionLogs`, `debug`, and `webWrapper`; see the [field reference](/cloud-connectors/aws/workloads/lambda/instrument#odigos_lambda_config-reference)). The only exception is `WEB_SERVER` mode with
[`existingLoaderValue`](#normal-functions-vs-web-server-functions), which also writes your loader variable
back unchanged. Everything else is generated by the layer at startup: the SDK
settings and a small collector config are built from `ODIGOS_LAMBDA_CONFIG` when the function cold-starts.

Your function's OpenTelemetry SDK does **not** send data to your destination directly. It sends it to a
small collector that ships inside the Odigos layer and runs in the same Lambda sandbox, reachable on
`localhost`. That collector then forwards the data to your real destination — **after** your handler has
already returned its response to the caller.

That extra hop is the entire point: if your destination is slow or briefly unreachable, the delay lands on
billed duration rather than on the response your user is waiting for. (A `decouple` processor inside the
collector keeps the sandbox alive just long enough to finish sending before Lambda freezes it, so a
low-traffic function doesn't lose its telemetry.)

<Warning>
  Configure the destination only through `destination`. The layer clears any `OTEL_EXPORTER_OTLP_*`
  endpoint, protocol, headers, and insecure variables you set before it starts your function, so they have
  no effect — and pointing the SDK straight at your destination would put the network call back on the
  critical path of every invocation.
</Warning>

<Warning>
  `ODIGOS_LAMBDA_CONFIG` must stay valid JSON in the format the layer expects (version 2, which needs layers
  `v0.0.19` or newer; an older layer can't read it and the function fails to start). If it doesn't parse, or its
  version, signals, or endpoint are invalid, the layer prints an error starting with `odigos-lambda-startup:`
  (for example `odigos-lambda-startup: invalid Odigos Lambda configuration JSON`), and the function **fails to initialize**. Let the construct write it rather than editing it by hand.
</Warning>

## Where the layer comes from

<ParamField path="layerSource" type="OdigosLayerSource" default="ODIGOS_PUBLIC">
  Which copy of the OpenTelemetry layer your functions attach.
</ParamField>

| | `ODIGOS_PUBLIC` (default) | `IN_ACCOUNT` |
| --- | --- | --- |
| What it adds to your stack | Just a reference to a layer | A nested stack per language/architecture in use |
| Who owns the layer | Odigos' AWS account | **Your** account, created by your own stack |
| When it's resolved | At build time, from a table inside the package | At deploy time, from AWS Serverless Application Repository |
| Works without a fixed region | No — needs a concrete region | Yes |
| First deploy | Unchanged | Slower |

```typescript
import { OdigosLambdaInstrumentation, OdigosLayerSource } from '@odigos/aws-cdk';

new OdigosLambdaInstrumentation(this, 'Odigos', {
  destination: { endpoint: 'otlp.example.com:4317' },
  functions: [fn],
  layerSource: OdigosLayerSource.IN_ACCOUNT,
});
```

Both options install byte-for-byte identical instrumentation. **`IN_ACCOUNT` is the SAR preload path for
CDK**: the construct nests an AWS Serverless Application Repository application into your stack, which
publishes an `AWS::Lambda::LayerVersion` owned by **your** account and wires its ARN onto the function. You
do not deploy SAR by hand when using this option.

Use `IN_ACCOUNT` if your organization's policy forbids attaching a Lambda layer owned by an outside AWS
account. It needs the principal running `cdk deploy` to hold `serverlessrepo:CreateCloudFormationTemplate`
and `serverlessrepo:GetApplication`.

For the same preload outside CDK (Console, CloudFormation/SAM) — or to see the Application IDs and
`SemanticVersion` the construct pins — see
[Preload the Lambda layer](/cloud-connectors/aws/workloads/lambda/preload).

<ParamField path="layerVersion" type="lambda.ILayerVersion">
  Escape hatch: attach a specific layer you already own, and **skip `layerSource` entirely** — neither
  `ODIGOS_PUBLIC` nor `IN_ACCOUNT` is consulted when this is set.

  Pass any CDK [`ILayerVersion`](https://docs.aws.amazon.com/cdk/api/v2/docs/aws-cdk-lib.aws_lambda.ILayerVersion.html)
  — typically `LayerVersion.fromLayerVersionArn(...)` pointing at a layer you mirrored into your account, or
  a `LayerVersion` construct you already defined. There is no separate allow-list: the construct attaches
  whatever you pass.

  This overrides the **SDK layer only**. For ADOT distros, the separate collector layer is still resolved
  from `layerSource` unless you also pass [`collectorLayerVersion`](#adot-and-application-signals).

  The layer **must** be the Odigos OpenTelemetry layer for the function's distro (same bytes / script layout
  as the public or SAR layer). The exec wrapper assumes paths inside that layout; a different layer will
  attach but fail to instrument at runtime. It also needs to be a `v0.0.19`-or-newer layer, which contains the
  startup launcher that reads `ODIGOS_LAMBDA_CONFIG`.

  ```typescript
  import * as lambda from 'aws-cdk-lib/aws-lambda';

  new OdigosLambdaInstrumentation(this, 'Odigos', {
    destination: { endpoint: 'otlp.example.com:4317' },
    functions: [fn],
    layerVersion: lambda.LayerVersion.fromLayerVersionArn(
      this,
      'OdigosLayer',
      'arn:aws:lambda:eu-west-1:111122223333:layer:odigos-otel-python-arm64:1',
    ),
  });
  ```

  One `layerVersion` is used for **every** function on this construct, so those functions must share a
  language, architecture, and distro that match that layer. Prefer `layerSource` when you need the construct to pick
  the right layer per function.
</ParamField>

## Choosing a distro

<ParamField path="distro" type="string">
  The ID of the instrumentation distro to apply — for example `java-lambda-otel-wrapper`. Left unset, each
  function gets the default distro for its language.
</ParamField>

A distro is the SDK or agent, the layer(s) that carry it, and the exec wrapper that loads it. The IDs are the
same ones Central shows on a source's status badge. The full list, with what each one covers, is on
[Lambda instrumentation distros](/cloud-connectors/aws/workloads/lambda/distros).

| Language | Default | Alternatives |
| --- | --- | --- |
| Java | `java-lambda-otel-agent` (full agent) | `java-lambda-otel-wrapper`, `java-lambda-otel-proxy-wrapper`, `java-lambda-otel-sqs-wrapper`, `java-lambda-otel-stream-wrapper`, `java-lambda-adot`, `java-lambda-adot-application-signals` |
| Node.js | `nodejs-lambda-otel` | `nodejs-lambda-adot`, `nodejs-lambda-adot-application-signals` |
| Python | `python-lambda-otel` | `python-lambda-adot`, `python-lambda-adot-application-signals` |
| Ruby | `ruby-lambda-otel` | None |

```typescript
new OdigosLambdaInstrumentation(this, 'OdigosJava', {
  destination: { endpoint: 'otlp.example.com:4317' },
  functions: [javaFn],
  distro: 'java-lambda-otel-sqs-wrapper',
});
```

The distro you pass is looked up against **each function's own language**. A construct that sets `distro`
and holds functions in more than one language therefore fails the build for the ones that don't match:

```text
Unsupported Lambda distro java-lambda-otel-wrapper for python
```

**Define one construct per language whenever you set `distro`.** This is also why `distro` isn't a good fit for
the [Aspect](#instrumenting-every-function-in-a-stack) in a stack with mixed languages. Constructs that leave
`distro` unset can mix languages freely.

The ADOT distros only run on the runtimes ADOT supports (Java 11, 17, 21; Node.js 18.x, 20.x, 22.x, 24.x;
Python 3.10 through 3.13). Using one on another runtime stops the build:

```text
Lambda distro java-lambda-adot does not support runtime java8.al2
```

<Info>
  In the Odigos UI, a Lambda source's distro can also be changed from the source drawer. For a self-managed
  function, set the same `distro` here — Odigos checks your deployed function against the distro selected in
  Central, and reports **Instrumentation does not match** if they differ. See
  [Switch distros](/cloud-connectors/aws/workloads/lambda/distros#switch-distros).
</Info>

## ADOT and Application Signals

The ADOT distros run the [AWS Distro for OpenTelemetry](https://aws-otel.github.io/) SDK instead of the
upstream OpenTelemetry layer. Select one with [`distro`](#choosing-a-distro). They differ from the other
distros in a few ways that matter in CDK.

**Two layers.** An ADOT function gets an SDK layer (`odigos-otel-adot-<language>-<arch>`) and a separate
collector layer (`odigos-otel-adot-collector-<arch>`). That's two of the five layer slots AWS allows per
function. Both are recorded in tags: `odigos:sdk-layer` and `odigos:collector-layer`.

<ParamField path="collectorLayerVersion" type="lambda.ILayerVersion">
  The collector layer to attach for an ADOT distro. Only needed when you supply your own ADOT SDK layer with
  [`layerVersion`](#where-the-layer-comes-from): `layerVersion` replaces the SDK layer only, so pass the
  matching collector layer here. The two must match the function's architecture. Non-ADOT distros don't use
  this option.
</ParamField>

**`IN_ACCOUNT` nests two applications.** With `layerSource: IN_ACCOUNT`, an ADOT function adds **two**
Serverless Application Repository applications to your stack: the SDK layer for that language and
architecture, and the collector layer for that architecture. See
[Preload the Lambda layer](/cloud-connectors/aws/workloads/lambda/preload).

**Telemetry goes to your destination, and Application Signals is off.** The signals you enable on
`destination` are exported through the collector layer to your destination. The plain ADOT distros force
CloudWatch Application Signals off at startup, even if the function sets
`OTEL_AWS_APPLICATION_SIGNALS_ENABLED=true`.

### Application Signals

The `java-lambda-adot-application-signals`, `nodejs-lambda-adot-application-signals`, and
`python-lambda-adot-application-signals` distros run ADOT with
[CloudWatch Application Signals](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-application-signals.html)
enabled. They're in beta. Beyond the two layers, the construct does three extra things:

- **Attaches the execution-role policy.** It adds the AWS managed policy
  `CloudWatchLambdaApplicationSignalsExecutionRolePolicy` to the function's role.
- **Requires traces and metrics.** Set both `destination.traces` and `destination.metrics` to `true`. If
  either is off, the build stops with
  `ADOT + Application Signals requires traces and metrics to be enabled for the destination.`
- **Warns you to enable the service.** It emits a synth warning to enable CloudWatch Application Signals
  service discovery.

<Warning>
  Enable Application Signals service discovery **once per AWS account and region** before the first deploy.
  The construct can't do it for you. Application Signals also sends service telemetry to AWS in addition to
  your Odigos destination.
</Warning>

At runtime the function exports to your Odigos destination over OTLP as usual, and also mirrors its enriched
spans to Lambda's embedded AWS agent. The metrics AWS derives from those spans stay in CloudWatch; they are
not forwarded to your destination. If you pass an imported role, it must allow
`CloudWatchLambdaApplicationSignalsExecutionRolePolicy` or already have it attached.

## Normal functions vs. web-server functions

<ParamField path="mode" type="OdigosInstrumentationMode" default="HANDLER">
  `HANDLER` is for an ordinary Lambda function — one that exports a handler and gets invoked per event.

  `WEB_SERVER` is for a function that runs an actual web server behind the
  [AWS Lambda Web Adapter](https://github.com/awslabs/aws-lambda-web-adapter).
</ParamField>

The difference matters because both Odigos and the Web Adapter want to use the same Lambda setting
(`AWS_LAMBDA_EXEC_WRAPPER`) to hook into startup. In `WEB_SERVER` mode, Odigos sets it to
`/opt/odigos-webserver` and **records the wrapper the function already had** (for example the adapter's
`/opt/bootstrap`) in its configuration. At startup, the Odigos wrapper loads instrumentation and then hands
control to that original wrapper.

<Warning>
  **Using `HANDLER` on a web-adapter function overwrites the adapter's setting and
  the function stops serving traffic.** There's deliberately no auto-detection:
  spotting the adapter would mean inspecting the function's other layers, which CDK
  often can't resolve until deploy time — and a detector that was right most of the
  time would silently break exactly the functions it got wrong. So you state it.
</Warning>

```typescript
import * as lambda from 'aws-cdk-lib/aws-lambda';
import { OdigosLambdaInstrumentation, OdigosInstrumentationMode } from '@odigos/aws-cdk';

const webFn = new lambda.Function(this, 'WebFn', {
  // ...
  environment: {
    AWS_LAMBDA_EXEC_WRAPPER: '/opt/bootstrap',   // the adapter's wrapper, set in CDK as usual
  },
});

new OdigosLambdaInstrumentation(this, 'Odigos', {
  destination: { endpoint: 'otlp.example.com:4317' },
  functions: [webFn],
  mode: OdigosInstrumentationMode.WEB_SERVER,
});
```

<Warning>
  CDK can only record a wrapper it can see. **The function's existing `AWS_LAMBDA_EXEC_WRAPPER` must already be
  in its CDK `environment`** when the construct runs — otherwise nothing is recorded, and the adapter's own
  wrapper is replaced instead of chained.
</Warning>

<ParamField path="existingLoaderValue" type="string">
  Only used in `WEB_SERVER` mode. If the function already sets its language's startup variable —
  `NODE_OPTIONS`, `JAVA_TOOL_OPTIONS`, or `PYTHONPATH` — you can pass its value here. The construct writes it back as **your value, unchanged**; Odigos
  adds its own part at runtime, so you never add Odigos flags yourself.

  If you've already set the variable in the function's own `environment`, you can leave this out: the
  construct then writes nothing for that variable and your value stays as defined.
</ParamField>

Not every distro can run in `WEB_SERVER` mode. Only the default distros with a verified web-server loader are
accepted: the Java full agent, `nodejs-lambda-otel`, and `python-lambda-otel`. `WEB_SERVER` rejects:

- **Ruby**, with `Web-server instrumentation is not supported for ruby`.
- **ADOT and the lightweight Java wrappers**, with `Unsupported Lambda distro <name> for <language>`.
- **The deprecated [`javaHandlerDistro`](#java-the-deprecated-javahandlerdistro) on a Java function**, with
  `Java handler adapters require HANDLER mode`.

<Info>
  The distro rules for web-adapter functions are the same ones listed on
  [Lambda instrumentation distros](/cloud-connectors/aws/workloads/lambda/distros#functions-behind-the-aws-lambda-web-adapter).
</Info>

## Java: the deprecated `javaHandlerDistro`

Java functions now default to the **full OpenTelemetry agent** (`java-lambda-otel-agent`), which works with
both `RequestHandler` and `RequestStreamHandler` functions. To use a lightweight wrapper instead, set
[`distro`](#choosing-a-distro).

<ParamField path="javaHandlerDistro" type="OdigosJavaHandlerDistro" deprecated>
  **Deprecated — use `distro`.** Still accepted, so existing apps keep building. Each value maps to a
  `distro` ID:
</ParamField>

| `javaHandlerDistro` | Use `distro` instead |
| --- | --- |
| `OTEL_HANDLER` | `java-lambda-otel-wrapper` |
| `OTEL_PROXY_HANDLER` | `java-lambda-otel-proxy-wrapper` |
| `OTEL_SQS_HANDLER` | `java-lambda-otel-sqs-wrapper` |
| `OTEL_STREAM_HANDLER` | `java-lambda-otel-stream-wrapper` |

`javaHandlerDistro` only applies to Java functions. Setting both `distro` and `javaHandlerDistro` stops the
build with `Use distro or legacy javaHandlerDistro, not both`.

<Warning>
  The lightweight wrappers are a correctness setting, not a level of detail. The generic wrapper installs a
  `RequestHandler` implementation, so a function that implements `RequestStreamHandler` has a different method
  signature and the generic wrapper **breaks the invocation**. Match the wrapper to your handler's input type, as
  described in [Choosing a Java distro](/cloud-connectors/aws/workloads/lambda/distros#choosing-a-java-distro).
</Warning>

<Note>
  The default changed from the generic wrapper to the full agent. If you previously relied on the default,
  set `distro: 'java-lambda-otel-wrapper'` explicitly to keep the lightweight behavior.
</Note>

## Instrumenting every function in a stack

```typescript
import { Aspects } from 'aws-cdk-lib';
import { OdigosInstrumentationAspect } from '@odigos/aws-cdk';

Aspects.of(stack).add(new OdigosInstrumentationAspect(stack, {
  destination: { endpoint: 'otlp.example.com:4317' },
}));
```

This visits every Lambda function in the stack.

<ParamField path="skipUnsupportedRuntimes" type="boolean" default="false (true on the aspect)">
  What to do when a function's runtime has no OpenTelemetry layer (Go, .NET, custom runtimes).

  The aspect defaults to `true`: skip it with a build **warning** rather than failing. The single-function
  construct defaults to `false`, because naming one specific Go function and asking for it to be
  instrumented is a mistake worth stopping the build over.
</ParamField>

## Naming your service

`OTEL_SERVICE_NAME` is what your function shows up as in your observability tool.

<ParamField path="serviceName" type="string">
  Left unset, this becomes the function's real name when your stack sets one explicitly, and the function's
  CDK construct ID otherwise.
</ParamField>

That fallback exists for a structural reason: a function name that CloudFormation generates for you is a
reference to the function itself, and a function referring to its own generated name inside its own
configuration is a circular dependency that CloudFormation refuses to deploy.

<Warning>
  Odigos compares this against the source's service name, which is the function's real AWS name unless you
  override it in Odigos. **If your function's name is auto-generated, set `serviceName` explicitly** —
  otherwise Odigos reports it as drifted. Note that `serviceName` applies to *every* function in a single
  construct, so use one construct per function when you need different names.
</Warning>

## Debugging

<ParamField path="debug" type="boolean" default="false">
  Sets `"debug": true` in `ODIGOS_LAMBDA_CONFIG`, which turns on `OTEL_LOG_LEVEL=debug` for the function's OpenTelemetry SDK and collector, so span and OTLP-export
  diagnostics appear in the function's CloudWatch log group. Useful while wiring up a destination, expensive to
  leave on. Has no effect in `WEB_SERVER` mode.
</ParamField>

## Other things worth knowing

<AccordionGroup>
  <Accordion title="Functions this construct can't instrument">
    A container-image function (`DockerImageFunction`) can't carry Lambda layers at all. The construct also
    needs a function your own stack owns — one imported with `Function.fromFunctionArn` can't be modified
    by CDK.
  </Accordion>

  <Accordion title="Environment size">
    A Lambda function's environment is limited to 4096 bytes in total. `ODIGOS_LAMBDA_CONFIG` includes your
    destination headers, so a long credential plus your own variables can exceed it.
  </Accordion>

  <Accordion title="Layer limits">
    AWS allows a maximum of 5 layers per function; the ADOT distros use two of them. Also don't attach the Odigos layer through more than one
    route at once — AWS rejects a function that carries two versions of the same layer.
  </Accordion>
</AccordionGroup>

## API reference

| Export | What it is |
| --- | --- |
| `OdigosLambdaInstrumentation` | The construct. Methods: `instrument(fn)`, `instrumentAll(fns)`. |
| `OdigosInstrumentationAspect` | Applies instrumentation to every function in a scope. |
| `OdigosLayerSource` | `ODIGOS_PUBLIC` \| `IN_ACCOUNT` |
| `OdigosInstrumentationMode` | `HANDLER` \| `WEB_SERVER` |
| `OdigosJavaHandlerDistro` | **Deprecated.** The four Java handler wrappers; use the `distro` option instead. |
| `renderCollectorConfig` | Validates a `destination` and renders its inline collector configuration. The function itself now builds its configuration at startup from `ODIGOS_LAMBDA_CONFIG`. |
| `LAYER_ARNS`, `ODIGOS_VERSION` | The public layer-ARN table baked into the package (`ODIGOS_PUBLIC`), and the Odigos release it came from. |
| `SAR_APPLICATIONS`, `SAR_SEMANTIC_VERSION` | What `IN_ACCOUNT` deploys under the hood: SAR Application IDs keyed by `language/architecture`, and the pinned semantic version (same bytes as this package release). You normally do **not** import these — set `layerSource: IN_ACCOUNT` instead. Use them only if you're authoring your own SAR/`AWS::Serverless::Application` template; the step-by-step is in [Preload the Lambda layer](/cloud-connectors/aws/workloads/lambda/preload). |
